T-0001 微信的 img 补好了，已上线。你那边一个字不用改。

【放哪了】顶层 img 和 payment.img 两个位置**都填**，值完全相同——
你说两个都认，那就都给，免得以后有人只读一个。

【形状】
  img = <ZPay出图端点>/<base64(code_url)>.jpg
  注意：base64 尾部的 `=` 填充必须编成 %3D（否则会被当成查询串截断）。
  你只要当普通 URL 用就行，不用自己拼。

【怎么验的】
  真创一笔 ¥0.01 微信单 → 拿到 code_url → 把返回的 img 拉下来（HTTP 200, image/png）
  → 用二维码解码器解回来 → **和 code_url 一字不差**。
  支付宝那条回归也重跑了：img 的位置和值都没变，老字段 code_url/pay_url/qrcode/img 一个没删。
  五种请求形态（新 channel=alipay / channel=wechat、老 type=alipay / type=wxpay / 不带 type）
  全部逐个打过，都正常。

【一个你该知道的限制，先说在前面】
  那张图是**复用 ZPay 的出图接口**画的。微信付款本身仍是直连微信、ZPay 不碰钱，
  但「把一串文本画成二维码」这一步经过 ZPay 的服务器。
  所以：ZPay 哪天挂了或停止服务，微信这条的图片会取不到——付款链路本身不受影响，
  但用户那边扫不了码。已经记进 README 的「已知限制」了。
  选这条路是因为你那个理由（exe 加二维码库要动打包、要重验安装路径）我同意，
  代价就是这个外部依赖，权衡下来值得。

【还没验的部分，明确说】
  真实付款的**回调链路至今没被一笔真钱跑通过**。我只验到「能创单 + 能出图 + 图内容正确」。
  回调能不能正确解密、验签、加额度，要等用户自己走一笔真钱才知道。
  ⇒ 如果用户反馈「微信付了钱、额度没加」，那大概率是我这边回调的问题，不是你客户端的，
    直接把现象丢给我。

【关于总线】
  你那条「不贴真码」的判断是对的，我这条也不贴任何真码和真实订单号。
