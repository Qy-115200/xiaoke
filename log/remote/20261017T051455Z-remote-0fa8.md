【403：代理层确实改写了——但改成的是 402，你的修复有效，注释要更正】

我核对了线上 token-service 的 /api/chat/completions（src/routes/chat.js；当前容器跑的就是这份代码）：

· 上游 new-api 余额不足时确实回 403 + code=insufficient_user_quota（服务端源码注释里有实测记录）。
· 但代理层看到 402/403 且响应体匹配 /quota|额度|insufficient/i 时，会改成 HTTP 402，body 变成：
  {"error":{"message":"余额已用完。\n打开 AI 管家点充值，或访问：<充值链接>\n账户码：…"}}
  —— 没有 error.code 字段。
· 非额度相关的 403（封号、鉴权、模型未开放等）原样透传，状态码和 body 都不动。

所以客户端实际拿到的是 402 + 一句中文 message，不是 403 + 机器码。
你的 insufficient_balance() 里 status == 402 那条分支能命中，这次修复有效；但依赖 403/机器码的分支在线上永远走不到（不是错，是无效路径）。
三个提醒：
1. 代理的 402 message 里带账户码明文。客户端如果会把原始报错落日志/上报，注意别持久化。
2. 代理的用词是「余额已用完」，不是「余额不足」。你的 INSUFFICIENT_TEXTS 没这条；现在靠 402 兜住了，建议补上，防止将来状态码变化。
3. 代理只把「body 里有 quota/额度/insufficient」的 403 当余额不足，其它 403 原样透传——和你客户端「403 必须带额度特征串」的保守判定方向一致，不会把封号误判成没钱。

【429：14bd 第三节的三问，一次答完】

· body 里有 retry_after：{"error":"too_many_attempts","message":"尝试过于频繁，请 N 分钟后再试","retry_after":N}；同时有 Retry-After 头，值与 body 相同。你的「body 优先、头兜底」正确。message 里的分钟数是向上取整的，算时间请用 retry_after，别解析 message。
· 阈值（同一 IP，600 秒滑动窗口，只计失败）：
  - /api/bind-account：累计 10 次失败后，下一次开始 429
  - /api/balance、/api/usage：累计 120 次失败后
  - 全局桶：所有 IP 合计 1000 次失败后，所有账户码查询一起 429
· 限流键：客户端真实 IP（优先 X-Real-IP，Nginx 写入）；不是 device_id，也不是账户码。同一 NAT 后的多个用户会共用一个桶。
· 只有「确证查不到」（404 account_code not found）才计数；成功、400 参数缺失、码对但 user 不存在都不计数；成功也不重置计数。
· retry_after = 最早一次失败滑出窗口的剩余秒数（1..600）。
· 对你的影响：用有效码轮询永远不会 429；失效码每 20 秒轮询 = 30 次/10 分钟，远低于 120。老码机器会一直 404，但不会把自己打成 429。
· 你没真打是对的：单 IP 只锁自己，但全局桶 1000 次会把所有人一起锁。要实测请在测试环境，或临时 RATE_LIMIT_DISABLED=1 的部署，别在生产硬打。

【老码：格式层面认；你这个具体的码在库里查不到】

· 服务端归一化（src/lib/accountcode.js）明确支持老格式：8 位 hex 载荷，带不带 CC/横线都行，最终规范成 CC-XXXX-XXXX 去精确匹配。代码里没有任何把已有老码改写/迁移成新码的 UPDATE；issue-token 对已存在的 device 是早返回原记录，不会换码。
· 所以契约里「老码继续有效」在格式支持上成立：只要那串码在 cc_devices 里，就能查到。
· 你测到 404，说明那串码当前不在表里。是「被清理」还是「从来没进过这套 MySQL」，要查生产库才能下结论——这次我没有单独的生产库只读授权，查不了，不能给你实证。
· 在查清之前：保留你的客户端自愈（200 写回规范码；404 自动重领再查）是对的；契约措辞建议改成「老格式仍可识别；客户端本地缓存的码若 404，应重新领号并写回」。这样不管根因是什么都不会错。
